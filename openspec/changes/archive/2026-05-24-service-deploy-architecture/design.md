## Context

当前项目的“环境准备/初始化”与“应用服务运行”边界不清晰：后端进程在启动时可能包含准备数据、数据库启停/初始化等行为。这会带来：
- 部署不可预测：同一二进制在不同环境的副作用不同
- 可回滚性差：准备阶段与业务进程混在一起，难以做到“只回滚应用”
- 基础设施编排困难：数据库、网关、监控等组件无法统一用基础设施方式管理

本次设计将系统拆成两层：
- 基础设施层：MySQL（主从）、Nginx（网关）、Prometheus/Grafana（指标监控）、Loki（日志）
- 应用层：后端/前端，只依赖已就绪的基础设施，通过配置接入

约束与假设：
- 代码仓库仍保持单仓库管理前后端与部署资产
- 基础服务统一通过 Docker 部署，默认以 docker compose 作为本地与部署环境的最小实现
- deploy 目录位于仓库根目录（第一级目录），包含 compose 文件、配置与脚本；脚本负责“准备与编排入口”，但不侵入服务进程

## Goals / Non-Goals

**Goals:**
- 后端服务进程“纯粹化”：启动只做进程内初始化与对外提供服务，不执行跨进程准备（例如启动数据库、写入准备数据）
- 引入 deploy 目录(第一级目录)：收敛启动/初始化脚本与基础设施编排入口
- 引入 Nginx 网关：统一外部入口，转发 API 与服务静态资源
- 引入 Prometheus + Grafana：提供最小可用指标链路（metrics 暴露、采集、面板接入）
- 引入 Loki：提供最小可用日志链路（采集、存储、查询，并与 Grafana 集成）
- MySQL 主从：主写从读，提供读写分离的应用侧接入方式与最小故障策略

**Non-Goals:**
- 不在本次中实现复杂的权限/鉴权网关能力（如 OAuth2、WAF）；仅预留配置扩展点
- 不做多地域/多机房容灾与自动故障切换（HA/raft/Orchestrator 等），先以“可运行、可观测、可回滚”为优先

## Decisions

1) “准备”迁移到脚本，服务保持无副作用启动
- 决策：将准备数据、数据库初始化/迁移、必要的种子数据等，放入 deploy 或 scripts 下的可重复执行脚本；后端只在启动时校验依赖（连通性/配置）并提供服务。
- 替代方案：在后端启动时做“如果缺少就自动创建/迁移/导入”。缺点是服务启动含副作用、并发启动时竞态更复杂、回滚困难。

2) deploy 目录作为统一部署入口
- 决策：新增 deploy/ 目录，将基础设施 compose、初始化脚本、启动入口脚本放到此处；部署流程固定为：执行 deploy → 部署后端与前端。
- 替代方案：散落在各子目录（backend/scripts、ops、docker/）。缺点是入口分散、难以形成一致运行手册与自动化。

3) 基础服务统一通过 Docker（compose）部署
- 决策：将 MySQL（主从）、Nginx、Prometheus、Grafana、Loki（及日志采集侧组件）作为基础服务，全部通过 docker compose 在 deploy/ 中统一编排与启动。
- 替代方案：部分组件以宿主机进程/手工方式部署。缺点是环境不可复制、运维一致性差、脚本与配置难以收敛。

4) Nginx 作为网关
- 决策：Nginx 负责统一入口：/（前端静态）、/api（后端 API 反代）、/metrics（按需暴露或仅内网）。
- 替代方案：直接暴露后端与前端端口给外部。缺点是对外面向多个端口、跨域/HTTPS/缓存策略难统一。

5) Prometheus + Grafana 作为指标可观测性
- 决策：后端暴露 Prometheus metrics endpoint，由 Prometheus 抓取；Grafana 通过 datasource 展示面板。
- 替代方案：仅做日志，不做指标。缺点是容量趋势、延迟、错误率等关键 SLO 无法量化。

6) Loki 作为日志系统
- 决策：引入 Loki 作为日志存储与查询；日志采集侧组件（例如 promtail）从容器/文件采集并推送到 Loki；Grafana 增加 Loki datasource 用于日志检索。
- 替代方案：仅依赖容器日志或单机文件。缺点是跨实例查询困难、缺少统一检索与关联分析能力。

7) MySQL 主从与读写分离
- 决策：采用一个主库 + 一个从库的最小拓扑，复制由 MySQL 原生 replication 实现。应用侧通过两个 DSN 注入：WRITE_DSN（主库）与 READ_DSN（从库，允许回退到主库）。
- 替代方案：应用只连接单库。缺点是读扩展性差，且无法演进到读写分离。

8) 应用侧读写路由策略
- 决策：默认所有写走主库；读优先走从库，但满足以下回退：
  - 从库不可用时回退到主库读
  - 对一致性要求高的读（写后读）允许显式走主库（例如事务内读/关键接口）
- 替代方案：强制所有读走从库。缺点是一致性问题更明显，且从库故障会导致大量功能不可用。

## Risks / Trade-offs

- [主从延迟导致读到旧数据] → 应用提供“强一致读走主库”的能力；关键路径避免读从；必要时增加写后读窗口策略
- [初始化脚本不可重复执行导致幂等问题] → 所有准备脚本以幂等为第一原则（存在即跳过/基于版本表执行）；失败可安全重试
- [Nginx 路由变更影响现有调用方] → 保持对外路径尽量兼容；变更点集中在网关层，应用内部不依赖外部路径
- [监控组件增加资源与维护成本] → 先提供最小链路：后端 metrics + Prometheus scrape + Grafana 面板；告警后续迭代
- [日志组件增加资源与维护成本] → 先提供最小链路：日志采集 → Loki 存储/查询 → Grafana 检索；日志格式与保留策略后续迭代
- [读写分离改造影响数据访问层结构] → 明确 Repository/DAO 边界与路由规则；在关键接口先落地，再逐步扩大覆盖范围

## Migration Plan

1) 引入 deploy 目录与基础设施编排（先不改后端代码）
- 落地 Nginx、Prometheus、Grafana、MySQL 主从（以 compose 运行）
- 验证基础设施单独启动/停止与数据持久化

2) 后端纯粹化：剥离启动准备逻辑
- 将数据库初始化/迁移、种子数据导入迁移到脚本
- 后端启动只做配置校验与依赖连通性检查

3) 数据库读写分离改造
- 增加主/从连接配置与路由封装
- 逐步将读路径迁移到读连接，保留回退与强一致读入口

4) 引入 metrics 与监控面板
- 确认/补齐 metrics 暴露端点
- 配置 Prometheus 抓取与 Grafana datasource/基础面板

5) 引入 Loki 与日志检索
- 增加 Loki 与日志采集组件，并完成与 Grafana 的 datasource 集成
- 验证日志可被采集、在 Grafana 中可查询，并具备最小可用的检索维度（例如按服务/实例筛选）

6) 网关接入与对外入口切换
- 将外部访问切换到 Nginx
- 验证静态资源、API 路由、跨域/Headers 等

7) 回滚策略
- 网关、监控为旁路组件，可先停用不影响核心业务
- 数据库层面保留单写（主库）路径；从库异常时可回退为“主库读写”
- 后端纯粹化后，回滚仅需替换后端镜像/二进制，不影响基础设施

## Open Questions

- 后端当前是否已经暴露 metrics（或使用何种指标库）？若未提供，需要选定实现方式并统一路径与鉴权策略
- 当前数据库初始化/迁移机制是什么（手写 SQL、gorm auto-migrate、migrate 工具）？脚本如何做到幂等与可回滚？
- 日志采集侧组件采用何种方式（例如 promtail）以及日志标签规范（service/instance/env 等）如何约定以支撑检索与排障？
- Nginx 对外是否需要 TLS/证书管理（本地自签、生产 ACME）？本次是否只提供 HTTP？
