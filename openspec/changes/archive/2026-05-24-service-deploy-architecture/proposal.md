## Why

当前后端服务在启动时承担了“准备工作”（例如数据准备、数据库启停/初始化等），导致服务职责不纯粹、部署流程不可复用、环境差异（本地/测试/生产）难以标准化；同时缺少统一的网关与可观测性能力（指标/可视化/日志链路），排障与容量评估成本高。

需要将“准备与部署”从应用进程剥离到可复用的脚本与部署目录，并引入网关、监控与数据库主从，以支撑更稳定的上线、可扩展的架构演进与更低成本的运维。

## What Changes

- 将 server 的准备部分迁移到 shell 脚本中，后端进程只负责提供 HTTP 服务与业务逻辑，不再承担准备数据、开启/管理数据库等职责
- 在仓库第一级新增 deploy 目录，集中放置所有基础服务的 docker 编排（docker compose）、配置与启动/初始化脚本；部署时先执行 deploy 的内容，再部署后端与前端
- 引入 Nginx 作为网关，对前端静态资源与后端 API 做统一入口与路由转发
- 引入 Prometheus + Grafana 作为指标采集与可视化（监控）
- 引入 Loki 作为日志存储与查询，并与 Grafana 集成用于日志检索与排障
- MySQL 从单实例调整为主从模式：主库写入、从库读取（读写分离）
- 根据上述架构对相关代码与配置进行调整（包括数据库连接、读写路由、启动流程依赖等）
- 增加一个整体 README，介绍整体架构、目录、启动与部署顺序

## Capabilities

### New Capabilities
- `prepare-scripts`: 将环境准备、数据库初始化/迁移、必要的预置数据等流程收敛为可执行脚本（可在本地与部署环境复用）
- `deploy-layout`: 在仓库根目录新增 deploy 目录与统一的部署入口脚本，使用 docker compose 编排基础设施（网关/监控/日志/数据库）与应用的启动顺序
- `gateway-nginx`: 使用 Nginx 作为网关，统一入口、反向代理与静态资源服务，并为后续限流/鉴权/灰度预留扩展点
- `observability-prom-grafana`: 引入 Prometheus 与 Grafana，定义指标暴露、采集、告警/面板接入的最小可用链路
- `logging-loki`: 引入 Loki（及日志采集侧组件）并与 Grafana 集成，形成最小可用的日志查询链路
- `mysql-master-replica`: MySQL 主从复制与读写分离约定（主写从读、健康检查、故障处理的最小约束）
- `backend-pure-service`: 后端服务启动流程契约（无副作用启动、可在无数据库控制权限环境运行、依赖通过配置注入）

### Modified Capabilities
- (none)

## Impact

- 部署与运维：新增部署目录与脚本；启动流程改为“基础设施 → 应用（后端/前端）”
- 反向代理：引入 Nginx 配置与路由规则，影响现有对外访问方式与端口暴露
- 可观测性：新增 Prometheus/Grafana/Loki 依赖与指标/日志链路；需要在后端增加/确认 metrics 能力，并明确日志采集方式
- 数据库：MySQL 拓扑变更为主从；后端数据库连接与读写路径需要调整（可能涉及 DAO/Repository 或连接池管理）
- CI/CD：可能需要在流水线中增加 deploy 脚本执行步骤或 compose 编排步骤
